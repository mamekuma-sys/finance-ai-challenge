## 1. 제품 요약

### 1.1 한 줄 정의

**RWA Guard는 토큰증권의 발행 문서, 스마트컨트랙트 코드, 온체인 상태와 가격 사이의 불일치를 AI로 탐지하고 근거와 함께 경보하는 연속검증 서비스다.**

### 1.2 해결하려는 문제

토큰증권은 발행 단계의 스마트컨트랙트 결함뿐 아니라 유통 단계의 오라클 오류, 가격 조작, 발행조건 위반을 지속적으로 관리해야 한다. 그러나 현재 업무는 다음과 같이 분절되어 있다.

1. 발행 문서의 조건은 사람이 읽고 점검한다.
2. 컨트랙트 보안 검사는 별도 도구 또는 외부 감사에 의존한다.
3. 배포 후 온체인 상태와 가격은 또 다른 관제 시스템에서 감시한다.
4. 경보가 발생해도 문서 조항, 코드 라인, 트랜잭션을 한 번에 연결하기 어렵다.

이 때문에 “문서에는 발행 한도가 있지만 코드에는 제한이 없는 경우”, “오라클 가격이 기준가 범위를 이탈했지만 적시에 발견하지 못하는 경우”와 같은 통제 공백이 발생할 수 있다.

### 1.3 핵심 가치 제안

- **발행 전:** 발행 문서에서 통제조건을 추출하고 컨트랙트 구현 여부를 검사한다.
- **유통 중:** 모델 기반 기준가 밴드와 온체인 오라클 가격을 비교한다.
- **경보 시:** 문서 조항, 코드 라인, 데이터 출처, 트랜잭션 해시를 하나의 리포트로 연결한다.
- **의사결정:** 자동 승인 대신 담당자의 검토와 내부 승인 게이트를 지원한다.

### 1.4 주요 사용자

- **1차 사용자:** 증권사 토큰증권 보안·준법·리스크 담당자
- **2차 사용자:** 발행사 개발자, 내부감사 담당자, 금융보안 평가 담당자
- **최종 수혜자:** 토큰증권 투자자

## 2. 제품 비전과 원칙

### 2.1 제품 비전

토큰증권 발행에서 유통까지 “무엇이 약속되었고, 코드로 어떻게 구현되었으며, 현재 온체인에서 실제로 지켜지고 있는지”를 한 화면에서 증명한다.

### 2.2 제품 원칙

1. **근거 없는 판정 금지:** 모든 취약점과 경보에는 확인 가능한 증거를 첨부한다.
2. **AI와 결정론적 도구의 역할 분리:** AI는 문서·코드 의미 분석과 설명을 담당하고, 수치 계산과 이벤트 검사는 재현 가능한 로직으로 수행한다.
3. **사람이 최종 승인:** 서비스 결과는 사전 스크리닝과 승인 권고이며 법률·보안 전문감사를 대체하지 않는다.
4. **위험을 평균으로 희석하지 않음:** 치명적 보안위험과 가격위험을 별도 표시하고 종합위험은 가장 높은 위험을 우선 반영한다.
5. **증거 모드를 정직하게 표시:** P1 라이브 시뮬레이션은 실제 Kaia 테스트넷 트랜잭션과 receipt를 사용한다. 복구용 합성 이벤트는 `REPLAY`와 fixture 버전을 명시한다.

- 법적 발행 승인 또는 금융상품 인가 자동화
- 외부 전문 보안감사·감정평가의 완전한 대체
- 모든 RWA 유형을 지원하는 범용 가치평가
- 검증되지 않은 임의 바이트코드의 완전한 의미 복원
- Kaia 메인넷 또는 실제 투자자 자금 사용
- 경보에 따른 자동 거래정지·자금동결
- 실시간 뉴스 전체 수집 및 감성 기반 가격 예측
- 복수 기관용 권한관리와 엔터프라이즈 SSO

## 4. MVP 대상 시나리오

### 4.1 데모 자산

- 서울 소재 상업용 부동산을 기초로 한 목업 수익증권 1종
- 실제 공개 비교거래 데이터의 사전 적재 스냅샷 사용
- ERC-20 기반 목업 RWA 토큰과 가격 오라클 컨트랙트 사용
- 네트워크: Kaia Kairos 테스트넷

### 4.2 핵심 통제조건

샘플 발행 문서에서 다음 조건을 추출한다.

| 조건 | 예시 값 |
|---|---|
| 최대 발행량 | 100,000 토큰 |
| 발행 권한 | ISSUER_ROLE 보유 주소만 가능 |
| 담보/기초자산 확인 | 발행 전 collateralVerified=true 필요 |
| 오라클 갱신주기 | 최대 60분 |
| 가격 이상 기준 | 기준가 밴드 이탈이 연속 2회 이상 지속될 때 경보 |
| 비상 통제 | PAUSER_ROLE 보유자만 일시정지 가능 |

### 4.3 대표 결함

| 결함 | 취약 구현 | 기대 탐지 결과 |
|---|---|---|
| 접근권한 누락 | 누구나 mint 호출 가능 | Critical |
| 담보·발행한도 검증 누락 | 담보 확인 없이 최대량 초과 발행 가능 | Critical |
| 오라클 검증 누락 | 0, 음수 상당 값, 오래된 가격을 허용 | High |

## 5. 사용자 페르소나 및 핵심 과업

### 5.1 증권사 보안·준법 담당자 — 김지현

- 목표: 발행 전 중대한 통제 누락을 빠르게 선별하고 검토 근거를 남긴다.
- 어려움: 발행 문서와 Solidity 코드를 함께 이해하기 어렵고 검사 결과의 오탐 여부를 직접 확인해야 한다.
- 핵심 과업: “새 토큰증권을 검토할 때 발행조건이 코드에 구현되었는지 확인하고 담당자 승인 여부를 결정하고 싶다.”

### 5.2 시장감시 담당자 — 이도윤

- 목표: 유통 중 오라클 오류와 가격 이상을 조기에 발견한다.
- 어려움: 단순 가격변동만으로는 조작, 데이터 지연, 저유동성 노이즈를 구분하기 어렵다.
- 핵심 과업: “가격이 기준가를 벗어났을 때 일시적 노이즈인지 지속적인 무결성 문제인지 근거와 함께 알고 싶다.”

### 5.3 발행사 개발자 — 박서준

- 목표: 취약점의 위치와 수정 방법을 확인하고 재검증한다.
- 어려움: 정적분석 결과가 추상적이고 비즈니스 요구사항과 연결되지 않는다.
- 핵심 과업: “어떤 문서 조건을 어떤 코드가 위반하는지 확인하고 수정 후 통과 여부를 다시 검증하고 싶다.”

## 6. 핵심 사용자 여정

### 6.1 발행 전 검증

1. 담당자가 신규 자산을 등록한다.
2. 발행조건 문서를 업로드하거나 제공된 샘플 문서를 선택한다.
3. AI가 발행량, 권한, 담보, 오라클 조건을 구조화해 근거 문장과 함께 보여준다.
4. 담당자가 추출 결과를 검토·수정하고 확정한다.
5. Kaia 컨트랙트 주소 또는 Solidity 소스를 입력한다.
6. 서비스가 정적분석, 통제조건 비교, AI 의미 분석을 실행한다.
7. Exploit Risk와 발견사항이 코드 라인·문서 조항과 함께 표시된다.
8. 담당자는 수정 요청 또는 내부 검토 큐 이동을 선택한다.
9. 수정된 컨트랙트를 재검사하고 이전 결과와 비교한다.

### 6.2 유통 중 감시(P1 LIVE, P0 REPLAY)

1. 통과한 자산이 관제 홈에 등록된다.
2. 서비스가 기준가 밴드, 온체인 오라클 가격, 데이터 최신성을 표시한다.
3. 가격 변경 이벤트를 지속 수집한다.
4. 이탈 정도, 지속시간, 오라클 상태를 이용해 Price Integrity Risk를 계산한다.
5. 경보 조건 충족 시 관제 홈과 자산 상세에 경보를 생성한다.
6. 사용자는 경보 리포트에서 원인과 증거를 확인하고 상태를 확인/조사중/해결로 변경한다.

### 6.3 조작 시뮬레이션(P1)

1. 데모 운영자가 정상 상태의 자산 상세 화면을 연다.
2. 시뮬레이터에서 조작 강도와 지속 횟수를 선택한다.
3. 조작 주입을 실행하면 실제 Kaia 트랜잭션으로 목업 오라클 가격이 변경된다.
4. 트랜잭션 해시와 블록번호가 화면에 표시된다.
5. 이벤트 수집 후 가격선이 밴드를 벗어나고 경보가 생성된다.
6. 원인 분석 리포트가 기준가, 조작 가격, 괴리율, 지속시간, 트랜잭션을 연결해 보여준다.

## 7. 기능 범위 및 우선순위

### 7.1 우선순위 정의

- **P0 — 제출 계약:** 9월 7일 URL에서 실패 없이 작동해야 하는 핵심 수직 경로. 완료되지 않으면 다른 기능보다 먼저 수정한다.
- **P1 — 라이브 경쟁력:** 4인 병렬 개발로 구현하되, 9월 3일 통합 게이트를 통과한 기능만 제출판에 노출한다.
- **P2 — 발표심사·기관 PoC:** 본선 진출 이후 고도화하거나 대회 이후 확장한다.

| ID | 기능 | 우선순위 | 제출판 완료 경계 |
|---|---|---:|---|
| F1 | 자산 등록 및 샘플 데이터 선택 | P0 | 합성 자산 1종을 한 번에 불러오고 검증 흐름을 시작한다. |
| F2 | 발행 문서 통제조건 추출·확정 | P0 | PDF/텍스트에서 6개 조건과 페이지·문장 근거를 추출하고 사용자가 확정한다. |
| F3 | 컨트랙트 입력 및 3종 핵심검사 | P0 | 제공 fixture와 Solidity 직접 입력을 지원하며 3종 결정적 검사를 수행한다. |
| F4 | 문서–코드 불일치 분석 | P0 | 모든 확정 결과가 문서 근거와 코드 근거를 함께 가진다. |
| F5 | Exploit Risk 카드와 상세 리포트 | P0 | 규칙 기반 결과와 AI 검토 후보를 구분하고 Evidence Spine에 표시한다. |
| F6 | 관제 홈과 경보 피드 | P0 | 합성 사건과 `REPLAY` 이벤트를 포함한 제출용 상태판이 작동한다. |
| F7 | 기준가 밴드 vs 온체인가 차트 | P1 | 재현 가능한 스냅샷과 모델 버전을 표시하고 P0 결과를 방해하지 않는다. |
| F8 | 온체인 이벤트 수집과 가격 무결성 경보 | P1 | Kairos 이벤트를 중복 없이 수집하며 장애 시 명시적 `REPLAY`로 전환한다. |
| F9 | 실제 Kaia 조작 시뮬레이터 | P1 | allowlist 컨트랙트에서만 실행하고 receipt 확인 후 화면을 갱신한다. |
| F10 | 결과 재검사 및 전후 비교 | P0 | 취약본→수정본의 해결/잔존/신규 결과를 재현 가능하게 비교한다. |
| F11 | HTML 리포트와 JSON 증적 다운로드 | P0 | 문서→코드→체인/Replay→경보의 증거 계보와 버전을 내보낸다. |
| F12 | 재진입·외부호출·업그레이드 권한 검사 추가 | P2 | 본선 발표용 룰팩 확장으로 분리한다. |

| F15 | 다중 자산 유형과 상용 오라클 연동 | P2 | MVP는 합성 부동산 수익증권 1종과 Kairos에 고정한다. |

### 7.2 4인 팀 스코프 기준

현재 범위는 숙련도 차이를 포함해 약 **59~86인일**로 추정한다. 4명이 3~4주간 개발하는 규모에는 적정하지만, 2026년 8월 25일부터 제출일까지의 실제 기간은 약 13일이므로 P0와 P1의 완료 기준을 분리한다.

| 작업 묶음 | 예상 작업량 | 깊이 기준 |
|---|---:|---|
| 문서 AI 추출·근거·확정 | 8~12인일 | 단순 요약이 아니라 구조화 스키마, 원문 span, 사용자 확정을 포함한다. |
| 컨트랙트 정적분석·3종 룰 | 12~16인일 | Slither 출력만 보여주지 않고 AST/커스텀 룰과 fixture 평가를 포함한다. |
| 문서–코드 Evidence Spine | 7~10인일 | 문서 조건과 코드 실행경로를 같은 finding으로 연결한다. |
| 온체인 이벤트·시뮬레이터 | 9~13인일 | 실제 receipt와 재수집 커서를 사용하며 Replay를 명확히 구분한다. |
| 기준가·가격 무결성 | 6~10인일 | 고정 스냅샷, 재현 가능한 모델, 데이터 품질 상태를 포함한다. |
| UI·리포트·재검사 | 9~13인일 | 취약→수정 diff와 증적 다운로드가 하나의 사용자 여정으로 작동한다. |
| 통합·배포·반복 검증 | 8~12인일 | 10회 리허설, 장애 상태, 공개 URL 운영을 포함한다. |

### 7.3 범위 잠금

- **자산 유형 1개:** 합성 상업용 부동산 수익증권만 지원한다.
- **네트워크 1개:** Kaia Kairos만 지원한다.
- **통제조건 6개, 핵심 결함 3종:** 수를 늘리지 않고 증거 품질과 재현성을 높인다.
- **P0 입력 경계:** 제공 fixture와 Solidity 직접 입력을 공식 지원한다. 임의 주소의 검증 소스 자동 확보와 범용 프록시 해석은 P2다.
- **AI 판정 경계:** AI는 추출·매핑 후보·설명을 제공한다. 결정적 근거 없는 AI 단독 결과는 `확인 필요`이며 확정 Critical/High가 될 수 없다.
- **라이브 표시 경계:** 실제 RPC와 receipt가 확인된 데이터만 `LIVE`로 표시한다. 그 외는 `REPLAY` 또는 `검증 제한`으로 표시한다.
- **추가 기능 금지:** P0 수용 기준이 모두 통과하기 전에는 새로운 자산 유형, 검사 룰, 외부 알림을 추가하지 않는다.

## 8. 상세 기능 요구사항

### FR-01. 자산 등록

사용자는 신규 자산을 만들거나 데모용 샘플 자산을 한 번에 불러올 수 있어야 한다.

**필수 입력**

- 자산명
- 자산 유형
- 기초자산 설명
- 총 발행 예정량
- 네트워크 및 컨트랙트 주소
- 기준가 단위와 통화

**수용 기준**

- 샘플 불러오기 선택 시 5초 이내 필수 데이터가 채워진다.
- 필수값 누락과 잘못된 Kaia 주소 형식을 인라인 오류로 표시한다.
- 저장 후 자산 상태는 `검증 전`으로 표시된다.

### FR-02. 발행 문서 통제조건 추출

사용자는 PDF 또는 텍스트 발행 문서를 업로드할 수 있으며, 시스템은 지정된 JSON 스키마로 통제조건을 추출해야 한다.

**추출 필드**

- `max_supply`
- `authorized_minter`
- `collateral_requirement`
- `oracle_update_interval`
- `price_deviation_policy`
- `pause_authority`
- `effective_date`

**각 필드의 필수 메타데이터**

- 추출값
- 원문 인용 또는 문장
- 페이지 번호 또는 문단 식별자
- 신뢰도
- 사용자 확정 여부

**수용 기준**

- 샘플 문서의 필수 필드를 90% 이상 정확히 추출한다.
- 근거가 없는 필드는 값을 생성하지 않고 `확인 필요`로 표시한다.
- 사용자가 값을 수정할 수 있으며 수정 전후 값이 감사로그에 남는다.
- 업로드 문서의 지시문은 AI 시스템 명령으로 실행하지 않는다.

### FR-03. 컨트랙트 입력 및 출처 확인

사용자는 Solidity 소스를 붙여넣거나 Kaia Kairos 주소를 입력할 수 있어야 한다.

**수용 기준**

- 체인 ID, 주소, 소스 해시, 분석 시각을 기록한다.
- 소스가 검증되지 않았거나 주소에서 소스를 확보하지 못한 경우 `검증 제한` 상태를 표시한다.
- 분석할 수 없는 입력을 `안전함` 또는 `통과`로 판정하지 않는다.
- 프록시 컨트랙트 여부를 표시하며 P0에서 구현체를 확인할 수 없는 프록시는 수동 소스 입력을 요구한다.

### FR-04. 하이브리드 컨트랙트 검사

시스템은 결정론적 검사와 AI 의미 분석을 결합한다.

**P0 검사 범위**

1. 민팅·관리 함수의 접근권한 누락
2. 최대 발행량 또는 담보 확인 누락
3. 오라클 가격의 최신성·유효범위 검증 누락

**분석 파이프라인**

1. 소스 파싱 및 함수·수정자·상태변수 식별
2. Slither 등 정적분석 실행
3. 발행 문서 통제조건과 코드 구조 비교
4. AI가 비즈니스 로직 관점의 후보 결함 분석
5. 규칙·정적분석·AI 결과를 증거 기준으로 병합
6. 근거가 부족한 AI 단독 결과는 `확인 필요`로 분리

**발견사항 출력**

- 제목과 설명
- 심각도: Critical/High/Medium/Low/Info
- 판정 신뢰도
- 관련 문서 조항
- 관련 파일과 코드 라인
- 악용 또는 실패 시나리오
- 수정 가이드
- 탐지기와 룰 버전

**수용 기준**

- 제공된 취약·안전 fixture에서 핵심 3종 검사의 Precision과 Recall이 각각 80% 이상이어야 한다.
- 모든 Critical/High 결과는 코드 근거를 포함해야 한다.
- 동일한 입력과 룰 버전으로 재실행할 때 심각도와 핵심 결과가 동일해야 한다.
- 분석 실패 시 부분 결과를 통과 결과로 표시하지 않는다.

### FR-05. 문서–코드 불일치 분석

시스템은 확정된 발행조건을 코드와 비교해 구현 상태를 표시한다.

**상태**

- 구현됨
- 부분 구현
- 미구현
- 확인 불가

**수용 기준**

- 샘플 문서의 최대 발행량 100,000과 무제한 mint 구현 사이의 불일치를 Critical로 탐지한다.
- 담보 확인 조건이 문서에는 있으나 코드 실행경로에 없으면 Critical로 탐지한다.
- 오라클 갱신주기가 문서에 있지만 코드에 timestamp 검사가 없으면 High로 탐지한다.
- 각 불일치에서 문서 근거와 코드 근거를 같은 화면에 표시한다.

### FR-06. Exploit Risk Score

Exploit Risk는 0~100점이며 높을수록 위험하다. Security Score와 혼용하지 않는다.

**MVP 산정 방식**

| 심각도 | 기본 가중치 |
|---|---:|
| Critical | 40 |
| High | 25 |
| Medium | 10 |
| Low | 3 |

발견사항별 `기본 가중치 × 판정 신뢰도`를 합산하고 100점으로 제한한다. 단 하나의 확정 Critical이 존재하면 최소 80점으로 설정한다.

**등급**

- 0~19: Low
- 20~39: Guarded
- 40~59: Elevated
- 60~79: High
- 80~100: Critical

**수용 기준**

- 점수 옆에 산정에 영향을 준 상위 발견사항을 표시한다.
- 점수를 소수점 없이 표시하고 계산식과 룰 버전을 리포트에 저장한다.
- 확정 Critical을 다른 낮은 위험으로 평균내어 80점 미만으로 낮추지 않는다.

### FR-07. 기준가 밴드 생성 및 표시(P1)

기준가 수치는 LLM이 직접 생성하지 않는다. 사전 적재된 비교거래 데이터와 재현 가능한 통계 모델을 이용해 중심값과 범위를 계산한다.

**MVP 출력**

- 토큰 1개당 기준가 중심값
- 하단·상단 밴드
- 기준일과 데이터 최신성
- 표본 수
- 모델 버전
- 주요 설명변수
- 데이터 출처

**수용 기준**

- 동일 데이터와 모델 버전에서 동일한 결과를 반환한다.
- 차트의 기준가와 온체인가가 동일 통화·단위로 정규화된다.
- 데이터가 오래됐거나 표본이 부족하면 밴드를 숨기지 않고 신뢰도 경고를 표시한다.
- UI 문구는 `AI 적정가` 대신 `모델 기반 기준가 밴드`를 사용한다.

### FR-08. 온체인 이벤트 수집(P1)

시스템은 목업 토큰과 오라클의 필수 이벤트를 수집하고 중복 없이 저장한다.

**P1 라이브 이벤트**

- `PriceUpdated`
- `Minted`
- `Paused/Unpaused`

**수용 기준**

- 트랜잭션 해시, 블록번호, 이벤트 시각, 호출자, 이전값과 변경값을 저장한다.
- 동일 이벤트를 재수집해도 중복 레코드를 만들지 않는다.
- RPC 일시 장애 후 마지막 처리 블록부터 재수집한다.
- 최신 이벤트가 블록 확인 후 10초 이내 화면에 반영되는 것을 목표로 한다.

### FR-09. Price Integrity Risk Score(P1)

가격 무결성 위험은 다음 네 하위점수의 가중합으로 계산한다.

`Price Integrity Risk = 0.40D + 0.20P + 0.20O + 0.20Q`

- `D`: 기준가 밴드 이탈 정도
- `P`: 이탈 지속성
- `O`: 오라클 최신성·유효성
- `Q`: 기준 데이터 품질과 유동성 신뢰도

각 하위점수는 0~100이다.

**괴리 하위점수 예시**

- 밴드 내부: 0
- 밴드 밖 5% 이하: 25
- 5% 초과 15% 이하: 60
- 15% 초과: 100

**수용 기준**

- 점수와 함께 D/P/O/Q 기여도를 표시한다.
- 단발성 이탈과 지속 이탈을 구분한다.
- 문서상 허용 갱신주기의 2배 이상 가격이 갱신되지 않으면 오라클 상태를 Critical로 표시한다.
- 종합위험은 Exploit Risk와 Price Integrity Risk 중 높은 값을 기본값으로 표시하되 두 원점수를 항상 함께 제공한다.

### FR-10. 경보 생성 및 관리

**기본 경보 규칙**

- 확정 Critical 취약점 발견
- Price Integrity Risk 80 이상이 연속 2개 이벤트 또는 설정 시간 이상 지속
- 오라클 가격이 유효하지 않음
- 오라클 데이터가 문서상 갱신주기의 2배 이상 지연
- 최대 발행량 초과 또는 비인가 주소의 mint 탐지

**경보 상태**

- 신규
- 확인
- 조사중
- 해결
- 오탐

**수용 기준**

- 경보에는 발생시각, 자산, 심각도, 원인, 권장조치, 증거 링크가 포함된다.
- 사용자가 상태와 메모를 변경할 수 있다.
- 변경 이력과 수행자를 감사로그에 기록한다.
- 동일 원인과 이벤트로 중복 경보를 생성하지 않는다.

### FR-11. 관제 홈

관제 홈은 심사자가 10초 안에 전체 상태를 이해할 수 있어야 한다.

**필수 구성요소**

- 등록 자산 수
- Critical/High 자산 수
- 정상/주의/위험 신호등
- 자산별 Exploit Risk와 Price Integrity Risk
- 최근 경보 피드
- 데이터·오라클 최신성 상태

**수용 기준**

- 자산 카드 클릭 시 자산 상세로 이동한다.
- 최신 Critical 경보가 화면 상단에 표시된다.
- 빈 상태, 로딩 상태, 외부 서비스 장애 상태를 구분한다.

### FR-12. 자산 상세

**필수 구성요소**

- 모델 기반 기준가 밴드 vs 온체인 오라클 가격 차트
- 괴리율 및 Price Integrity Risk 추이
- Exploit Risk와 주요 발견사항
- 발행조건 구현 상태
- 경보 타임라인
- 최신 온체인 이벤트와 트랜잭션 링크

**수용 기준**

- 밴드와 가격선의 범례·단위·시간대가 명확하다.
- 차트 포인트 선택 시 기준가, 밴드, 온체인가, 괴리율을 보여준다.
- 경보 클릭 시 해당 시점과 트랜잭션을 강조한다.

### FR-13. 조작 시뮬레이터(P1)

시뮬레이터는 데모 권한이 있는 사용자에게만 노출한다.

**입력**

- 가격 변화율 또는 목표 가격
- 지속 업데이트 횟수
- 시나리오: 일시적 스파이크/지속 조작/오라클 지연

**수용 기준**

- 실행 전 테스트넷과 대상 주소를 명시하고 확인을 받는다.
- 실행 시 실제 Kaia 테스트넷 트랜잭션을 생성한다.
- 성공 후 트랜잭션 해시와 탐색기 링크를 표시한다.
- 실패 시 온체인 상태가 변경된 것처럼 표시하지 않는다.
- 반복 클릭과 과도한 트랜잭션을 방지한다.

### FR-14. 리포트와 증적

**P0 리포트 유형**

- 발행 전 검증 리포트
- 가격 무결성 경보 리포트

**필수 증적**

- 자산과 컨트랙트 식별정보
- 입력 문서·코드 해시
- 문서 조항과 코드 라인
- 사용한 데이터 출처와 기준시각
- 모델·프롬프트·탐지 룰 버전
- 위험점수 계산 내역
- 관련 트랜잭션 해시와 블록번호
- 생성시각
- 제한사항과 사람 검토 필요 문구

**수용 기준**

- 화면에서 읽을 수 있는 HTML 리포트를 제공한다.
- 동일 증적을 구조화 JSON으로 다운로드할 수 있다.
- 근거 링크가 없는 AI 서술을 Critical/High 판정의 근거로 사용하지 않는다.

### FR-15. 재검사와 전후 비교

**수용 기준**

- 기존 분석 결과를 보존한 채 새 Scan Run을 생성한다.
- 발견사항별 `해결/잔존/신규` 상태를 표시한다.
- 위험점수 변화와 수정된 코드 근거를 비교한다.
- 수정 컨트랙트의 Critical/High가 모두 해결되면 `자동검사 통과–담당자 검토 필요`로 표시한다.

## 10. AI 제품 요구사항

### 10.1 AI가 수행하는 일

1. 발행 문서에서 통제조건과 근거 문장을 구조화한다.
2. 정적분석 결과와 코드 구조를 비즈니스 로직 관점에서 해석한다.
3. 문서 조건과 코드 구현의 의미적 불일치 후보를 찾는다.
4. 검증된 증거를 바탕으로 사람이 읽을 수 있는 설명과 수정 가이드를 작성한다.

### 10.2 AI가 수행하지 않는 일

- LLM 단독으로 기준가 숫자를 생성하지 않는다.
- AI 단독 판정으로 발행을 승인하지 않는다.
- 근거가 없는 취약점을 확정 Critical로 표시하지 않는다.
- 업로드 문서에 포함된 명령을 시스템 명령으로 실행하지 않는다.
- 운영 키를 사용해 임의 온체인 트랜잭션을 생성하지 않는다.

### 10.3 AI 출력 통제

- 모든 에이전트 출력은 JSON 스키마로 검증한다.
- 분류·추출 작업은 낮은 변동성 설정을 사용한다.
- 문서·코드 청크 ID를 인용하지 못한 결과는 `확인 필요`로 낮춘다.
- 모델 버전, 프롬프트 버전, 입력 해시, 실행시각을 기록한다.
- 타임아웃 또는 오류 시 결정론적 분석 결과만 표시하고 AI 분석 실패를 명시한다.

### 10.4 최소 AI 평가셋

| 평가영역 | 최소 케이스 | 목표 |
|---|---:|---:|
| 문서 필드 추출 | 10 | 필수 필드 정확도 90% 이상 |
| 접근권한 결함 | 취약 2 / 안전 2 | Precision·Recall 80% 이상 |
| 담보·발행한도 결함 | 취약 2 / 안전 2 | Precision·Recall 80% 이상 |
| 오라클 검증 결함 | 취약 2 / 안전 2 | Precision·Recall 80% 이상 |
| 근거 인용 | 전체 Critical/High | 100% |

## 13. 비기능 요구사항

### 13.1 성능

- 관제 홈 초기 표시: p95 3초 이내
- 샘플 컨트랙트 전체 분석: 60초 이내
- 온체인 이벤트 반영: 블록 확인 후 목표 10초 이내
- 리포트 조회: 3초 이내

### 13.2 안정성

- 심사 기간 동안 공개 URL을 지속 제공한다.
- 외부 AI 또는 RPC 장애 시 서비스 전체가 흰 화면으로 실패하지 않는다.
- 사전 저장된 샘플 결과를 `Replay/샘플 결과`라고 명확히 표시한 복구 모드를 제공한다.
- `/health`에서 프론트, API, DB, RPC 상태를 확인할 수 있어야 한다.
- 배포 후 데이터베이스 마이그레이션과 샘플 시드가 자동 또는 문서화된 절차로 재현되어야 한다.

### 13.3 보안

- 비밀키와 API 키를 클라이언트 번들에 포함하지 않는다.
- 시뮬레이터 지갑은 테스트넷 전용이며 최소 잔액만 보유한다.
- 문서 업로드 크기와 형식을 제한하고 악성 파일 처리를 방지한다.
- 서버에서 업로드 콘텐츠를 명령으로 실행하지 않는다.
- 시뮬레이터 엔드포인트에 인증, rate limit, 대상 컨트랙트 allowlist를 적용한다.
- 로그에 비밀키, 전체 인증토큰, 민감한 원문을 남기지 않는다.

### 13.4 사용성

- 핵심 데모는 별도 회원가입 없이 샘플 모드에서 확인 가능해야 한다.
- 위험 색상만으로 상태를 구분하지 않고 텍스트·아이콘을 병행한다.
- 전문용어에는 툴팁을 제공한다.
- 모든 오류 메시지는 사용자가 다음 행동을 알 수 있도록 작성한다.

### 17.3 P1 승격 게이트

F7~F9는 다음 조건을 모두 충족할 때만 제출판의 `LIVE` 기능으로 승격한다.

1. 프로덕션 환경에서 실제 Kairos 트랜잭션 receipt와 이벤트가 연결된다.
2. 같은 이벤트를 재수집해도 중복 경보가 생기지 않는다.
3. RPC 장애가 P0 문서–코드 검증과 리포트 생성을 중단시키지 않는다.
4. LIVE 실패 시 자동으로 정상처럼 보이지 않고 `연결 지연` 또는 명시적 `REPLAY`를 표시한다.
5. 10회 통합 시나리오 중 9회 이상 조작→수집→경보→리포트가 완료된다.

### 17.4 기능 동결 원칙

- 9월 4일 이후 신규 P1 기능을 추가하지 않는다.
- P0 실패 수정, 데이터 정확성, 배포 안정성만 변경한다.
- 외부 API가 없어도 핵심 데모가 가능한 샘플 경로를 유지한다.

## 19. 출시 및 제출 체크리스트

### 제품

- [ ] 샘플 자산을 한 번에 불러올 수 있다.
- [ ] 발행 문서 조건과 근거가 표시된다.
- [ ] 취약 컨트랙트에서 핵심 3종 결함이 탐지된다.
- [ ] 수정 컨트랙트에서 Critical이 해결된다.
- [ ] P1 승격 시 실제 Kaia 트랜잭션 해시가 표시되며, 미승격 시 `REPLAY`가 명시된다.
- [ ] 조작 후 경보와 리포트가 생성된다.
- [ ] 모든 Critical/High에 확인 가능한 증거가 있다.
- [ ] AI·RPC 장애 상태가 사용자에게 명확히 표시된다.

### 제출 운영

- [ ] 웹서비스 URL이 비로그인 브라우저에서 열린다.
- [ ] 모바일이 아닌 일반 심사 노트북 환경에서 정상 작동한다.
- [ ] 환경변수와 비밀키가 저장소·클라이언트에 노출되지 않는다.
- [ ] `/health`가 정상 상태를 반환한다.
- [ ] 데이터베이스 시드와 마이그레이션 재현 절차가 있다.
- [ ] 기능명세서의 기능명과 실제 메뉴명이 일치한다.
- [ ] 외부 코드·데이터·아이콘의 라이선스와 출처가 정리돼 있다.
- [ ] 9월 7일 제출 직후부터 9월 11일까지 모니터링 계획이 있다.
