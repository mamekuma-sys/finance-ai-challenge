## 1. 재심 결론

### 본선 진출 가능성: **중**

0.3-r2는 2라운드의 핵심 지적을 피하지 않았다. `11-spec-draft.md` §4.5에는 순수 조건식,
전체 규칙 수집, `severity_rank`, `merge_key`, 전역 후속 규칙, 인수 스냅샷 5종이 들어갔다.
§2.1은 `core/showcase/nice`를 분리했고, §4.8은 민감 거래 필드와 상담원 핸드오프 경계를
하나의 선택안으로 고정했다. §5.4에는 지표별 분자·분모와 사전 임계값도 생겼다. 따라서
2라운드 당시의 “구현자가 빈칸을 임의 해석해야 하는 문서”에서는 분명히 전진했다.

그러나 **상**으로 올리기에는 이르다. 조치 엔진은 1,152개 상태 조합 모두를 어떤 규칙에는
연결하지만, 그 결과를 하나의 결정적 `AnalyzeResponse`로 만드는 계약은 아직 닫히지 않았다.
`unknown` 질문의 무조건 1순위 삽입은 이미 확인된 송금·원격제어 조치보다 질문을 앞세울 수
있고, 4개 초과 카드를 내리는 “다음 단계”는 응답 스키마에 필드가 없다. 스냅샷 d·e에는
규칙표와 알고리즘만으로 만들 수 없는 기대값도 들어 있다.

토큰은 `purpose_ack=true` 하나로 누구에게나 발급되어 목적 제한을 실제 권한으로 강제하지
못한다. 개인 부속면은 개인정보 경계를 잘 닫았지만, 새로고침·모바일 브라우저 축출 시 가장
가치 있는 거래 필드가 모두 사라지고 상담원에게 건네는 실제 동작이 정의되지 않았다. 또한
E2의 11개 코어 목록에 없던 F-20이 추가되어 코어가 12개가 되었고, 1인·약 6주 일정에서
100건 평가셋, 독립 라벨, PDF, SSE, 접근성, 브라우저 전용 문서, 규제 레지스트리까지 모두
삭제 불가로 묶였다.

현재 판정은 **“코어 구현을 시작할 가치는 있으나, M0가 완전히 끝났다고 선언해서는 안 되는
상태”**다.

| 심사위원 | 3라운드 한 줄 총평 |
|---|---|
| **A — 은행 사기대응 실무 팀장** | “3영업일 후속을 전역 규칙으로 올린 것은 맞지만, 이미 송금·원격제어가 확인된 사람에게 미확인 개인정보 질문을 1순위로 띄우면 소비자보호 승인은 내줄 수 없다.” |
| **B — 금융보안원 AI 보안 전문가** | “평가표와 토큰 엔드포인트는 생겼지만 `purpose_ack`는 인증이 아니며, MCP가 토큰을 획득·주입하는 경로와 4개 초과 행동의 응답 스키마가 없어 재현 계약은 아직 불완전하다.” |

## 2. 2라운드 잔여 개선 우선순위 TOP 5 추적

판정 기준은 2라운드와 같다.

- **해소:** 문서 안에서 원래 모순과 요구사항 누락이 닫혔다.
- **부분 해소:** 구조는 반영됐지만 구현 가능한 결정 규칙·성공 기준·증거가 부족하다.
- **미해소:** 원래 문제가 사실상 그대로 남았다.
- **새 문제로 전이:** 원래 표면 문제는 고쳤지만 수정 구조가 다른 실무 위험을 만들었다.

### 1위. 복합 상태 결정 엔진을 닫는다 — **새 문제로 전이**

**반영 근거**

- `11-spec-draft.md` §4.5는 조치 결정을 “6개 상태 필드의 모든 조합에 대해 정의된
  총함수”라고 선언하고, R1~R7을 열거형 기반 순수 조건식으로 바꿨다.
- §4.5.1은 “전체 수집 → 위해 정렬 → `merge_key` 병합 → 전역 필수 후속 → 금지 행동
  합집합 → 최대 4개 재번호”를 고정했다.
- §4.5.4는 요구된 복합 조합 a~e를 인수 스냅샷으로 넣었고, §9.3은 속성 기반 테스트와
  `already_sent` 전수 검사를 요구한다.

**재검증 경로와 판정**

6개 필드의 열거값을 전개한 1,152개 조합
(`3×4×4×4×2×3`)에 R1~R7의 `match`를 대입했다. **일치 규칙이 0개인 조합은 찾지
못했다.** 이 의미의 행 커버리지는 해소됐다.

그러나 출력의 결정성은 닫히지 않았다.

- §4.5.1 ②는 핵심 4축 중 하나라도 `unknown`이면 확인 질문 카드를 무조건 1번으로
  삽입한다. `already_sent + remote_control + personal_data=unknown`에서도 질문이
  기기 격리·지급정지보다 앞선다. 이는 위해 순위를 정의한 뒤 다시 무효화하는 우선순위
  역전이다.
- 규칙별 고유 `merge_key`를 합치면 1,152개 중 **874개가 4개를 초과**하고 최대 8개다.
  §4.5.1 ⑥은 초과분을 “다음 단계”로 접는다고 하지만 `AnalyzeResponse`에는
  `actions: ActionCard[]`만 있고 접힌 행동을 보존할 `next_steps` 필드가 없다.
- 같은 `call:bank_fraud`가 일반 연락, 지급정지 요청, 인증정보 노출 통지를 모두 병합한다.
  §4.5.1 ③은 높은 위해 행의 “카드 문구”를 따르면서 전체 행의 “목적 슬롯”을 합치라고
  하지만 `ActionCard`에는 목적 슬롯 필드가 없다. 지급정지 목적이 병합 뒤 실제 문구에
  남는지 기계적으로 결정할 수 없다.
- 네 핵심 축이 모두 `unknown`인 경우 R7은 질문을 최대 3개만 허용한다. 어느 축을
  제외할지 우선순위가 없다.

따라서 행 공백은 고쳤지만 **긴급 행동 우선순위 역전·초과 행동 소실·병합 목적 소실이라는
새 문제로 전이**됐다. 전체 조합 테스트의 실제 통과는 M단계 실증 사항이지만, 위 세 항목은
테스트 전에 문서 계약으로 먼저 고쳐야 한다.

### 2위. 코어 불변 `must`와 시연·확장 범위를 다시 나눈다 — **새 문제로 전이**

**반영 근거**

- `10-proposal-draft.md` §4.5와 `11-spec-draft.md` §2.1은
  `core/showcase/nice`를 분리하고, 코어 실패는 제출 차단, showcase 실패는 제외로
  정의했다.
- F-16·F-18은 showcase 1순위, F-12·F-15는 showcase 2순위로 내려갔다.
- `11-spec-draft.md` §3.3은 코어 장면에 100초, `/room`·`/safety`에 마지막 20초만
  배정했다.

**남은 문제**

티어 구분 자체는 해소됐다. 그러나 `15-revision-plan-r2.md` E2가 고정한 코어는
F-01·03·04·05·06·07·08·10·13·21과 F-19, 총 11개다. 개정 명세 §2.2는 E2에 없던
F-20 안전성 리포트를 “패널 합의문의 독립 평가”를 이유로 **새 코어로 추가**했고,
기획서 §4.5도 이를 따라 코어가 12개가 됐다. 이는 E2 계약의 명시적 목록과 불일치한다.

더 중요한 것은 12개라는 숫자보다 각 기능의 인수 깊이다. 1인이 약 6주 안에 자유 입력
이중 마스킹, LLM 3단계, 결정 엔진 전수 테스트, 이벤트 원장, 이중 문서 생성, 고령자·
WCAG 대응, SSE 타임라인, 100건 분리 평가셋, 독립 라벨 또는 대체 절차, 규제 템플릿
레지스트리까지 모두 배포 검증해야 한다. 일정·작업량·중간 탈락 기준이 문서에 없다.

결과적으로 “주변 기능도 모두 `must`” 문제는 고쳤지만, **제출 신뢰 장치까지 제품 기능
코어에 추가해 모든 것을 삭제 불가로 만든 일정 위험**으로 전이됐다.

### 3위. 브리핑의 개인정보 경계와 은행 효용을 함께 설계한다 — **새 문제로 전이**

**반영 근거**

- `11-spec-draft.md` §4.8은 금융회사명·송금 시각·금액대·수취 정보 메모를 브라우저에서만
  입력하고 서버 전송·저장·모델 입력·`sessionStorage` 저장을 모두 금지한다.
- 같은 절은 v1 핸드오프를 “사용자가 본인 기기에서 제시하거나 본인이 직접 전송”하는
  사용자 매개 방식으로 고정하며, 서비스 전송 채널·상관키는 범위에서 제외한다.
- `10-proposal-draft.md` §6.3은 재질문 수와 초기 정보 수집 시간을 부속면 포함 조건의
  합성 상담 시뮬레이션으로 한정했다.

**재심 판단**

2라운드가 요구한 세 선택지 중 하나를 명확히 골랐으므로 **민감 필드 처리와 핸드오프 경계의
문서 계약은 해소**됐다.

다만 §5.1은 부속면 4종을 브라우저 메모리에만 두고 “탭 이탈·새로고침 시 소멸”시킨다.
송금 직후 사용자는 같은 휴대전화에서 전화 앱으로 전환하거나, 상담 대기 중 브라우저가
재로딩될 가능성이 높다. 이때 은행 재질문을 줄이기 위해 방금 입력한 핵심 필드가 전부
사라진다. §4.8에는 “직접 전송”을 위한 파일 형식, 모바일 저장·공유 동작, 저장 전 이탈
경고, 재입력 비용이 정의되지 않았다. 개인정보 최소화와 구매자 효용의 충돌은
**휘발성·사용자 수동 전달 UX 문제로 전이**됐다.

브라우저 무전송은 문서 계약으로 해소됐고 NF-09 계측은 M단계에서 증명해야 한다. 반면
새로고침·백그라운드 복귀·인쇄·파일 공유가 실제 상담 흐름에서 되는지는 모바일 실증 없이는
해소로 판정할 수 없다.

### 4위. AI 기여와 안전성 평가의 판정 규칙을 사전 고정한다 — **부분 해소**

**반영 근거**

- `11-spec-draft.md` §5.4.1은 지표별 분자·분모, 사건 단위 집계, Wilson 95% 구간을
  표로 정의했다.
- §5.4.2는 PII 누출 0건, 템플릿 경계 위반 0건, 위험군 FN ≤10%, 인젝션 성공 ≤5%,
  citation validity ≥95%, fallback correctness 100%를 평가 전 고정한다.
- §5.4.3은 예비 평가 명명과 라벨러·불일치 처리 원칙을 적었고, §9.16은 규칙형 폼과
  LLM 보조 비교를 인수 기준으로 연결했다.

**남은 문제**

2라운드 M0 조건 4는 **제품 KPI·안전성 지표·AI 기여 비교 모두의 분자·분모·통과
임계값**을 요구했다. 현재 숫자 임계값은 안전성 지표 6개와 Rule 0 시간에만 있다.
오행동률, 브리핑 필드 충족률, 상담 재질문 수, AI 기여 4개 하위 지표에는 표본 수, 코딩
규칙, 성공 임계값이 없다. `unsafe action rate`, FP, 유보율에도 배포 판단 기준이 없다.

또한 §5.4.1은 표에 9개 지표 행을 두면서 기획서 §5.5는 “7개 지표”라고 부른다. 모든
비율에 Wilson 구간을 붙인다고 했지만, 임계값을 점추정치와 비교하는지 신뢰구간 상한·하한과
비교하는지도 없다. 적대셋 20건에서 성공 0건이어도 Wilson 95% 상한은 약 16.1%이므로,
`≤5%`를 어느 값에 적용하는지에 따라 동일 결과의 합격·불합격이 달라진다.

평가 실행과 프롬프트 비노출, 실제 라벨 일치도는 M단계 실증 사항이다. 그러나 위 성공 기준은
실행 전에 문서로 더 고정해야 한다.

### 5위. 행동 이벤트 원장과 API 보안 계약을 구현 수준으로 구체화한다 — **부분 해소**

**반영 근거**

- `11-spec-draft.md` §4.1·§4.6은 단일 현재값을
  `{event_id, action_id, occurred_at, state, source, previous_state}`의
  `ActionFactEvent[]`로 교체하고 `user_reported_receipt_confirmed`로 개명했다.
- §4.1·§4.2는 `POST /api/v1/tokens`, TTL 10분, `analyze:free_text`, Bearer 헤더,
  해시 보관, 폐기 API, `text`와 `masking_confirmed=true`의 JSON Schema 조건,
  MCP 동일 토큰을 명시했다.

**남은 문제**

이벤트 배열과 명칭은 문서 계약으로 대부분 해소됐다. 다만 “정정 이벤트”에는
`event_type`이나 `corrects_event_id`가 없어 어떤 과거 사건을 정정하는지 재현할 수 없고,
브라우저 로컬 배열은 서버 감사 원장이 아니라 사용자 기기의 **로컬 행동 이력**이다.

API 쪽은 더 크게 남았다. `{ purpose_ack: true }`만 보내면 인증·클라이언트 등록·사용자
세션 없이 토큰이 발급된다. 이는 고지를 읽었다는 자기선언이지 목적 제한을 강제하는
권한 증명이 아니다. 공격자는 새 토큰을 반복 발급하고
`masking_confirmed=true`도 자기선언할 수 있다. 토큰 발급 쿼터·바인딩·`audience`·
재사용 제한의 숫자 계약이 없고, MCP 클라이언트가 MCP 외부의 REST 발급 엔드포인트에서
토큰을 얻어 Streamable HTTP 요청 헤더에 주입하는 부트스트랩 흐름도 정의되지 않았다.

저장소·로그 누출, 토큰 재사용·우회, MCP 직접 입력은 M단계 공격 테스트가 필요하다. 그러나
발급 주체와 토큰 전달 흐름은 테스트 전에 문서 계약으로 고쳐야 한다.

## 4. 새로 드러난 결함

### 4.1 §4.5는 행 커버리지는 있지만 결정적 출력 총함수는 아니다 — **치명도 높음**

이번 검증에서 R1~R7의 조건 자체가 비는 조합은 찾지 못했다. 문제는
`IncidentState → AnalyzeResponse`가 하나로 정해지지 않는다는 데 있다.

1. `unknown` 축이 여러 개일 때 최대 3개 질문의 선택·순서가 없다.
2. 4개 초과 행동을 접는다고 했지만 응답 스키마에 접힌 목록이 없다.
3. 같은 `merge_key`에서 높은 위해 행의 문구와 모든 행의 목적을 합치는 방법이 없고,
   `ActionCard`에도 `purpose_slots`가 없다.
4. 전역 후속을 어느 카드의 `required_followup`에 붙이는지, 별도
   `procedure:written_followup` 카드로 만드는지 두 표현이 공존한다.
5. `do_not_show_when`은 이름상 노출 조건식인데 규칙 표에는 “재판정 대기”, “상대 제공
   링크 사용” 같은 금지 행동 문구가 들어간다. 조건과 사용자 경고가 한 필드에 섞였다.

이는 구현 실증 문제가 아니라 **문서 타입·병합 계약의 결함**이다.

#### 스냅샷 5종 재계산

| 스냅샷 | 판정 | 규칙표·알고리즘 대입 결과 |
|---|---|---|
| a | **부분 일치** | R1+R3의 고유 키 4개 순서는 표와 맞는다. 그러나 “높은 severity인 R1 문구를 따름”과 “지급정지 목적까지 병합”을 동시에 구현할 목적 슬롯이 없다. |
| b | **부분 일치** | R2+R3+R4를 4개 키로 줄이는 순서는 맞는다. 금융회사 카드 하나에 지급정지·인증정보 통지를 합치는 정확한 문구 조립 계약은 없다. |
| c | **부분 일치** | R4+R7은 고유 키 6개다. 표의 보이는 4개는 만들 수 있지만 접힌 `verify:official_channel`·`call:1332`를 응답에 보존할 필드가 없다. |
| d | **불일치** | R3은 카드 3개만 만든다. `family_proxy` 수정자는 모든 카드에 고지를 붙인다고만 했지, 기대값의 “4 본인 제한 절차 안내” 카드를 생성할 `merge_key`·순위·알고리즘 단계가 없다. |
| e | **불일치** | R5+R7의 카드 4개 순서는 만들 수 있다. 그러나 기대 금지 행동의 “기기 상태 확인 전 해당 기기 금융 앱 사용 권유”는 R5·R7의 금지 행동 합집합에 없고 별도 전역 규칙도 없다. |

스냅샷은 인수 기준으로서 유용하지만, 현재 두 건은 알고리즘의 결과가 아니라 알고리즘 밖의
희망 결과다.

### 4.2 R3~R5 비배타화와 R7 최우선 규칙이 과잉 카드·긴급 행동 지연을 만든다 — **치명도 높음**

R3~R5를 자기 축만 보게 바꾼 목적은 복합 피해 축을 빠뜨리지 않는 것이다. 그러나
`credential=suspected + personal_data=suspected`만으로도 R4+R5의 고유 행동이 6개다.
모든 고위험 축이 겹치면 최대 8개가 되고, 4개 제한 때문에 낮은 severity 축의 행동은
보이지 않는 “다음 단계”로 내려간다. 응답 필드가 없으므로 현재 계약상 사실상 소실될 수 있다.

더 위험한 것은 R7이다. 1,152개 중 **498개는 이미 `already_sent` 또는 기기 침해가
확인됐으면서 다른 핵심 축에 `unknown`이 있는 조합**이다. 이 모두에서 §4.5.1 ②가 확인
질문을 1번 카드로 올린다. “미확인은 보수적으로 묻는다”가 “확인된 긴급 행동보다 먼저
묻는다”로 바뀌었다.

R6·R7 사이에 아무 규칙도 적용되지 않는 구멍은 찾지 못했다. 다만 `safe_device_available`
자체의 `unknown`은 R7 조건에 없고, 기기 상태까지 `unknown`일 때 안전 기기 확인·금지
행동은 규칙 행이 아니라 §4.4 설명과 스냅샷 e에 흩어져 있다. 안전 기기 전제를 독립
수정자나 전역 규칙으로 만들지 않으면 채널별 구현이 달라질 수 있다.

### 4.3 개인 부속면은 개인정보를 지키지만 실제 통화 핸드오프를 보장하지 않는다 — **치명도 중간**

브라우저 전용·무저장은 타당한 개인정보 선택이다. 그러나 은행 상담의 첫 행동은 전화이고,
같은 모바일 기기에서 다이얼러를 열면 사용자는 부속면을 상담원 화면과 동시에 제시할 수 없다.
새로고침이나 메모리 회수 뒤에는 입력도 사라진다. “본인이 직접 전송”한다는 문구만으로는
파일 생성, OS 공유 시트, 인쇄 실패, 저장 전 이탈을 처리할 수 없다.

무저장 원칙을 바꿀 필요는 없다. 대신 저장·공유 완료 전 다이얼러 이동 경고, 사용자 명시적
PDF/인쇄 생성, 생성 뒤 메모리 즉시 삭제, 지원 브라우저·실패 폴백을 문서로 정해야 한다.
수용 가능성은 iOS·Android에서 백그라운드 복귀, 새로고침, 파일 공유, 실제 모의 통화로
검증해야 한다. 현재 계약만으로는 UX 비용을 수용 가능하다고 판정할 수 없다.

### 4.4 `purpose_ack` 토큰은 목적 제한 권한이 아니라 공개 비용 게이트에 가깝다 — **치명도 높음**

`POST /api/v1/tokens`는 `{purpose_ack:true}` 외에 아무 자격도 요구하지 않는다.
금지 목적의 호출자도 같은 값을 보낼 수 있다. 토큰·IP·패턴 쿼터를 언급하지만 발급 빈도,
토큰당 호출 수, 동시성, `audience`, 클라이언트 바인딩, 반복 재발급 차단 값이 없다.
따라서 토큰 탈취보다 먼저 **정상 발급 절차 자체의 자동화 남용**이 가능하다.

MCP에서는 더 현실적인 흐름이 빠졌다. `analyze_scam`만 제공하면서 토큰 발급은 MCP 도구가
아닌 REST 엔드포인트다. 어느 주체가 동의 화면을 보여주고, 토큰을 받아, MCP 연결의
Authorization 헤더에 넣고, 만료 때 재발급하는지 계약이 없다. 자유 텍스트 MCP를 유지하려면
클라이언트 등록·인가 및 토큰 전달 흐름을 별도로 설계해야 한다. 6주 MVP에서는 MCP를
`scenario_id` 전용으로 제한하고 자유 텍스트를 비활성하는 편이 문서의 목적 제한 주장과
실제 통제를 일치시킨다.

### 4.5 평가 계약은 숫자가 생겼지만 합격 의미가 아직 하나로 고정되지 않았다 — **치명도 중간**

지표 행은 9개인데 “7개 지표”라고 부르고, 배포 임계값은 6개에만 있다. AI 기여 비교는 네
하위 지표를 나열하지만 표본 수·참가자·채점척도·최소 개선폭이 없다. 오행동률과 상담
재질문 수도 통과선이 없다.

Wilson 구간을 모두 공개하면서 임계값은 점추정치·구간 경계 중 무엇과 비교할지 적지 않았다.
작은 셋을 “예비 평가”로 제한한 것은 정직하지만, 배포 차단 계약은 동일 결과를 두 사람이
다르게 판정할 수 없어야 한다. 이 항목은 실제 수치를 채우는 M단계 전에 문서에서 닫아야 한다.

### 4.6 12개 core는 1인·6주 일정에서 인수 깊이까지 달성하기 어렵다 — **치명도 높음**

문서에는 기능별 예상 공수, 주차별 게이트, 중간 실패 시 축소 가능한 경계가 없다. 특히
F-20은 단순 페이지가 아니라 평가셋 분리·라벨·실패 사례·구간·버전 증적을 포함하고,
F-08은 서버 PDF와 브라우저 전용 문서라는 두 구현이다. F-03·04·13은 LLM·SSE·폴백과
결합하며 F-10·NF-05는 전 코어 화면의 접근성 검증을 요구한다.

기능 수만 세어 “불가능”이라고 단정하지는 않는다. 그러나 현재 계약에는 6주 가능성을
입증할 작업 분해나 이미 구현된 자산이 없다. 문서 근거만으로는 **core 12개 전부를 현재
인수 깊이로 완성할 가능성을 낮게** 본다. F-20은 제품 기능 티어가 아니라 제출 전
`release gate`, F-19는 정적 제출물, F-13은 showcase 후보로 다시 분류할 필요가 있다.

### 4.7 로컬 이벤트 배열은 정정 가능한 이력이지만 감사 “원장”은 아니다 — **치명도 중간**

`ActionFactEvent[]`는 2라운드의 단일값 덮어쓰기를 고쳤다. 그러나 `previous_state`만으로는
어느 이벤트를 정정했는지, 여러 탭·시계 변경·중복 클릭을 어떤 순서로 환원할지 정할 수 없다.
`sessionStorage`는 사용자와 브라우저 스크립트가 바꿀 수 있으므로 기관 증거 또는 감사
로그로 해석해서도 안 된다.

문서에서 `event_type=observation|correction`, `corrects_event_id`, 현재 상태 환원 규칙,
중복 이벤트 처리와 클라이언트 시각의 비신뢰성을 정의하고, 외부 표시는 “로컬 행동 이력”으로
낮추는 것이 정확하다. 실제 append-only UI와 새로고침 복구는 M단계에서 검증해야 한다.

## 5. 심사위원별 재판정

### A — 은행 사기대응 실무 팀장

**판정: 중**

R3를 독립 규칙으로 만들고 3영업일 절차를 전역 후속으로 올린 점, 개인 부속면에 상담 필드를
되살린 점은 2라운드보다 낫다. 복합 피해를 단일 대표 상태로 잘라내지 않겠다는 방향도 맞다.

그러나 소비자보호 관점에서 우선순위는 질문 수보다 중요하다. 이미 송금 완료·원격제어가
확인됐는데 다른 축의 `unknown` 때문에 확인 질문이 1순위가 되는 것은 승인할 수 없다.
개인 부속면도 실제 전화 전에 저장·공유하지 않으면 상담 중 쓸 수 없다.

**한 줄 총평:** “공식 절차는 살아났지만, 확인된 긴급 조치가 미확인 질문보다 항상 앞선다는
불변식을 문서와 테스트로 고정하기 전에는 현장 승인 불가다.”

### B — 금융보안원 AI 보안 전문가

**판정: 중하**

순수 조건식, 평가 전 설정 버전 관리, Wilson 구간, 토큰 해시 보관, 입력 비반사 오류는
검토 가능한 계약이다. 사용자 사건과 부속면을 서버에 남기지 않는 데이터 경계도 일관된다.

반면 `purpose_ack`는 인증이 아니고, MCP의 토큰 획득·주입 흐름도 없다. 평가 임계값의
비교 대상과 제품 KPI 통과선이 비어 있으며, `AnalyzeResponse`가 4개 초과 행동을 표현하지
못한다. 문서가 안전성을 주장하려면 스키마와 판정 결과가 재현 가능해야 한다.

**한 줄 총평:** “보안 통제의 이름은 갖췄지만, 공개 토큰 발급과 응답 스키마 구멍 때문에
공격자와 구현자가 같은 계약을 다르게 해석할 수 있다.”

### C — 서비스 기획 출신 벤처 심사역

**판정: 중**

30초 데모에서 악성 앱 상태를 추가하자 금지 행동·안전 기기·3영업일·부속면이 함께 바뀌는
장면은 기억에 남는다. 공개 상황실을 마지막 20초로 내린 것도 집중도를 높인다.

하지만 12개 코어 전부가 삭제 불가이고, 구매자 효용의 핵심인 부속면은 새로고침 한 번에
사라진다. REST·MCP가 showcase로 내려갔어도 “코어 직후 최우선”이라 일정 압력이 남는다.
6주 MVP라면 심사에서 보일 하나의 완성된 상담 전 흐름이 기능 수보다 중요하다.

**한 줄 총평:** “훅은 선명해졌지만, 지금 범위대로면 기억나는 데모를 만들고도 완성도 부족으로
구매 이유를 잃을 위험이 크다.”

## 7. 패널 합의문

### M단계 진입 여부: **조건부 동의**

패널은 주제 재탐색이나 전면 폐기를 권하지 않는다. 긴급 우회로, 상태별 결정 엔진, 사용자
매개 브리핑이라는 코어 가설은 구현으로 검증할 가치가 있고, E1~E8의 대부분이 문서에 실제로
옮겨졌다.

다만 2라운드에서 M단계 선행 조건으로 둔 M0 네 계약 중 1번과 4번이 아직 부분 충족이다.
따라서 **현재 명세 전체의 동시 구현에는 동의하지 않는다.** 다음을 진입 조건으로 한다.

1. §4.5에 긴급 상태 우선 불변식, 복수 `unknown` 선택, 초과 카드 응답 필드, 병합 목적
   슬롯, proxy·safe-device 수정자를 추가하고 스냅샷 5종을 알고리즘으로 다시 산출한다.
2. 제품 KPI·AI 기여의 표본·채점·통과선과 안전성 임계값의 구간 비교 방식을 평가 실행 전에
   고정한다.
3. 자유 텍스트 MCP의 토큰 획득·주입·남용 통제를 닫지 못하면 v1에서는 합성
   `scenario_id` 호출만 허용한다.
4. E2와 다른 F-20 추가를 재결정하고, 12개 코어를 런타임 코어·정적 제출물·release gate로
   분리한 6주 임계 경로를 고정한다. 이 결정 뒤에는 새 core를 추가하지 않는다.

개인 부속면의 모바일 저장·공유와 무전송, 토큰 공격 내성, 1,152개 조합, 평가 수치는
문서만으로 증명할 수 없으므로 M단계 초반 게이트로 실증한다. 이 실증에서 실패하면 관련
효과 주장을 낮추거나 showcase를 제외해야 하며, 코어 안전 규칙을 축소해서 맞춰서는 안 된다.

권고 구현 순서는 `Rule 0 정적 카드 → 결정 엔진 전수 테스트 → 행동 이벤트 이력 →
규제 문구·브리핑 → AI 보조 → 독립 평가`다. F-16·F-18·F-12·F-15는 이 경로와 보안
게이트가 통과한 뒤에만 활성한다.

**최종 합의:** “M단계 진입에는 조건부로 동의한다. 다만 총함수·평가 합격선·MCP 인증·6주
코어 범위를 먼저 다시 동결하고, 그 전에는 안전·확장 기능의 병렬 구현을 시작하지 않는다.”
