### 1.1 조건 1 상세 검증

#### 긴급 우선 불변식 직접 대입

3라운드 반례인
`already_sent + remote_control + personal_data=unknown + safe_device=yes`를 대입하면
R2(severity 1), R3(severity 3), R7(severity 7)이 일치한다. 미확인
`personal_data`의 잠재 severity는 6이고 현재 확인된 최고 severity는 1이다.
`6 < 1`이 거짓이므로 §4.5.1 ②에 따라 질문은 R2·R3 유래 긴급 카드 뒤로 간다.
병합 뒤 금융회사·112·인증수단 복구·서면 후속이 노출 4개를 차지하고 질문은
`next_steps`로 내려간다. 따라서 패널 A가 지적한 **질문 1순위 역전 자체는 해소**된다.

다만 같은 문서 안에 다음 잔존 문구가 있다.

- §4.4 `transfer_state=unknown`: “송금 여부 확인 질문을 최우선 삽입”
- §4.5.3 R7 뒤 설명: “확인 질문 카드는 §4.5.1 ②에 따라 1번 카드가 된다”

예를 들어 `transfer=unknown + device=remote_control`은 새 §4.5.1에 따르면 기기 긴급
행동 뒤에 질문이 와야 하지만, 위 두 문구를 따르면 질문이 1번이다. §4.5.1을 우선한다는
충돌 해소 규칙이 없으므로 구현자는 두 결과를 만들 수 있다.

#### 엣지 탐색

- **잠재 severity 동률:** 현재 매핑은 `device=1, transfer=3, credential=4,
  personal_data=6`으로 모두 다르고, 한 축은 동시에 `unknown`과 확인 상태일 수 없다.
  따라서 현 열거형에서 도달 가능한 잠재 severity 동률은 없다. 동률 반례를 만들 수
  없었으므로 이번 판정의 미충족 사유로 삼지 않는다.
- **현재 확인 severity가 없는 경우:** 미확인 축은 있으나 severity 1~6의 확인 위험이 없는
  조합이 존재한다. 보조 전수 열거에서는 90개였다. §4.5.1은 이때 비교할 “현재 확인된 최고
  severity”의 기본값을 정하지 않는다. R7의 rank 7을 비교 기준으로 쓸지, 질문을 무조건
  1번에 둘지 명시해야 한다.
- **질문·전역 후속·proxy의 상한 경쟁:** `already_sent`이면서 다른 핵심 축에
  `unknown`이 있는 조합은 222개이고, 그중 `family_proxy`는 111개다. 이 111개는
  질문, 항상 노출해야 하는 서면 후속, “마지막 노출 순위” proxy 카드가 함께 생기며
  고유 키가 4개를 초과한다. §4.5.1은 서면 후속과 proxy를 위해 어느 일반 긴급 카드를
  `next_steps`로 내릴지 예약·축출 순서를 정하지 않았다.
- **서면 후속 중복:** R3이 이미 `procedure:written_followup`을 행동으로 수집하고 병합한
  뒤, §4.5.1 ④가 같은 `merge_key`의 독립 카드를 다시 “생성”한다. 병합은 ③에서 먼저
  끝난다. `already_sent` 384개 조합 모두에서 ④를 기존 카드의 승격·재사용으로 볼지
  두 번째 카드 생성으로 볼지 갈린다.
- **`next_steps` 타입:** §4.1의 `ActionCard.priority`는 `1 | 2 | 3 | 4`뿐인데
  `next_steps`도 `ActionCard[]`다. 보조 열거의 최대 고유 키는 proxy 포함 9개라 노출
  4개 뒤에 5개가 접힐 수 있다. 접힘 목록을 전체 순위 5~9로 둘 수도, 목록 안에서
  1부터 다시 번호를 매길 수도 없어 현재 타입만으로는 순서를 하나로 직렬화할 수 없다.
- **병합 출처:** §4.5.1 ③은 `purpose_slots`와 템플릿 버전의 합집합은 정하지만,
  `ActionCard.official_source`는 단일 `string`이다. R1+R3+R4처럼 서로 다른 공식
  출처를 병합한 카드에서 어느 출처를 남길지 정해지지 않았다.

보조 열거는 6개 상태 필드의 1,152개 조합에 R1~R7의 `merge_key`, 전역 후속, proxy
수정자를 대입했다. 고유 키 4개 초과는 890개, 최대는 9개였다. 이 수치는 구현 성능 주장이
아니라 상한·타입 충돌 경로를 찾기 위한 문서 규칙 전개 결과다.

### 1.2 조건 2 상세 검증

§5.4.1의 9행, §5.4.2의 여섯 배포 차단 임계값, 점추정치 판정은 서로 모순이 없다.
예를 들어 적대셋 20건 중 공격 성공 1건은 점추정치 5%이므로 `≤5%`를 통과하고,
Wilson 상한은 판정에 관여하지 않는다. 이 부분은 동일 결과에 동일 판정을 낸다.

제품 KPI 표는 F2의 수치를 옮겼지만 다음 경계가 남는다.

1. **KPI ①:** p95 ≤2초의 N, 측정 기간, 재시도 포함 여부, p95 산식(최근접 순위/보간)이
   없다. 같은 지연 표본도 산식에 따라 경계값 판정이 달라질 수 있다.
2. **KPI ③:** 100%의 분모가 “평가 중 생성한 모든 브리핑”, 홀드아웃 40건, 또는 별도
   스키마 회귀셋 중 무엇인지와 최소 N이 없다.
3. **KPI ④:** 미포함 조건 중앙값이 0일 때 “30% 이상 감소”의 계산·판정을 정하지 않았다.
   동일 사건의 쌍체 비교 여부도 §5.4.3 표 안에는 없다.
4. **KPI ⑤:** 규칙형 폼의 사실 추출 누락률이 0일 때 상대 20% 감소는 정의되지 않는다.
   §9.16은 확인 질문 수·브리핑 슬롯 정확도·이해도도 비교하지만, 이 세 하위 결과가
   KPI ⑤의 최종 통과 여부에 관여하는지 아니면 공개만 하는지 명시하지 않는다.

따라서 명칭·점추정치·주요 초기값은 닫혔지만, 요청된
“동일 결과에 두 사람이 다른 판정을 내릴 수 없다” 기준에는 아직 미달한다.

### 1.3 조건 3 상세 검증

## 2. 스냅샷 a~e 재계산

명세서 §4.5.4의 기본값 문구를 적용하되, 스냅샷 e는 `transfer_state` 기본값 결함을
별도로 표시했다.

|---|---|---|
| **a** | `R1(rank 2)+R3(rank 3)` → 병합 전 키는 `device:isolate`, `call:bank_fraud`, `call:112`, `procedure:written_followup`. 병합하면 금융회사 카드에 R1 전제와 R1·R3 목적 슬롯이 합쳐진다. 노출은 1 기기 격리 → 2 금융회사 → 3 112 → 4 서면 후속, `next_steps`는 없음이다. 금지 행동은 R1∪R3∪safe-device 수정자로 계산된다. | **부분 도출.** ④가 R3의 기존 후속 카드를 재사용한다고 해석하면 일치하지만, 문언대로 새로 생성하면 같은 키 카드가 중복된다. |
| **b** | `R2(rank 1)+R3(rank 3)+R4(rank 4)` → `call:bank_fraud`는 3개 행, `call:112`는 3개 행, `action:credential_recovery`는 R2+R4로 병합되고 서면 후속이 남는다. 노출 4개는 기대값과 같고 `next_steps`는 없음, 금지 행동은 R2∪R3∪R4∪safe-device 수정자다. | **부분 도출.** a와 같은 전역 후속 중복 문제가 있고, 병합된 서로 다른 공식 출처를 단일 `official_source`에 넣는 규칙이 없다. |
| **c** | `R4(rank 4)+R7(rank 7)`. transfer 질문의 잠재 3이 확인 최고 4보다 높으므로 질문 1번. 이어 금융회사·112·인증수단 복구가 노출되고, R7의 `verify:official_channel`, `call:1332`는 이 순서로 `next_steps`에 남는다. 금지 행동은 R4∪R7이다. | **카드 집합·순서는 도출 가능.** 다만 `next_steps` 항목의 `priority`를 현재 `ActionCard` 타입으로 표현하는 방식은 미정이다. |
| **d** | `R3(rank 3)`의 금융회사·112·서면 후속 뒤 §4.5.1 ⑤가 `notice:proxy_scope`를 마지막 노출 카드로 생성한다. `next_steps`는 없고 금지 행동은 R3∪proxy다. 3라운드에 없던 proxy 카드 생성 근거가 생겨 기대 4개가 규칙 안으로 들어왔다. | **부분 도출.** proxy 자체는 도출되나 a와 같은 서면 후속 중복 해석이 남는다. 더 복잡한 proxy 조합에서는 강제 카드 슬롯 배정도 미정이다. |
| **e** | 의도대로 `transfer=not_sent`를 보충하면 `R5(rank 6)+R7(rank 7)`. device 질문 잠재 1이 확인 최고 6보다 높아 1번, 이후 접촉 중단, 병합된 공식 채널 확인, 병합된 1332가 오며 `next_steps`는 없다. 금지 행동은 R5∪R7∪safe-device 수정자로, 미확인 기기의 금융 앱 사용·검색이 포함된다. | **부분 도출.** safe-device 수정자로 기대 금지 행동은 도출된다. 그러나 §4.5.4는 미지정 축 기본값을 `none`이라고만 써서 `none`이 허용되지 않는 `transfer_state`가 빠진 e는 문언상 유효한 `IncidentState`가 아니다. |

결론적으로 d의 proxy 카드와 e의 safe-device 금지 행동은 3라운드보다 분명히 개선됐지만,
스냅샷 5종 모두를 **추가 해석 없이** 스키마까지 포함해 기계적으로 산출한다는
§4.5.4의 선언은 아직 성립하지 않는다.

## 4. 최종 판정

### M0 계약 동결 선언 가능 여부: **조건부**

**현재 상태로 즉시 “M0 계약 동결 완료”를 선언할 수는 없다.** 조건 3과 4는 충족했지만,
조건 1과 2가 부분 충족이어서 3라운드 §7의 네 진입 조건이 모두 닫히지 않았다.

동결 선언 전에 남은 조건은 다음 두 묶음이다.

1. **결정 엔진:** R3/전역 후속을 단일 카드로 만드는 승격·중복 제거 시점, 질문·서면
   후속·proxy의 노출 슬롯 예약과 축출 순서, 위험 확인값이 없을 때의 비교 기준,
   `next_steps` 순번 타입, 병합 출처 배열, §4.4·§4.5.3 잔존 우선순위 문구,
   스냅샷 e의 `transfer=not_sent` 기본값을 한 번에 고정한다.
2. **평가:** KPI ①·③의 N·모집단·산식, KPI ④·⑤의 기준값 0 처리와 쌍체 비교,
   KPI ⑤ 하위 지표가 최종 통과에 미치는 규칙을 평가 실행 전에 고정한다.

위 두 묶음이 문서에서 닫히면 조건 3·4를 다시 열지 않고 M0 동결을 선언할 수 있다.
그 전의 결정 엔진·평가 구현은 서로 다른 해석을 코드에 굳힐 위험이 있으므로 M단계 착수
승인은 보류한다.
