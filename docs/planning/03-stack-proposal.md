## 제안 스택 (TypeScript 단일 스택)

| 레이어 | 선택 | 이유 |
|---|---|---|
| 프레임워크 | **Next.js (App Router) + TypeScript** | 프론트+API 단일 레포, Codex 위임 효율, 생태계 |
| 배포 | **Vercel** (Pro 아니어도 무방) | 무중단 신뢰성·자동 스케일, 심사 기간 방치 가능 |
| LLM | **Claude API** — 판정·에이전트 sonnet 계열, 경량 분류 haiku | 한국어 품질, 구조화 출력, 스트리밍 |
| 오케스트레이션 | Vercel AI SDK + 자체 경량 상태 기계 (프레임워크 비도입) | 6개 에이전트 파이프라인은 명시적 코드가 디버깅·심사 설명에 유리 |
| 실시간 | **SSE** (Server-Sent Events) | Vercel 함수와 호환, WebSocket 인프라 불요 |
| DB | **Neon Postgres** (serverless) | 무료 티어로 충분, 관리형 무중단, 사건·수법 DB 저장 |
| MCP 서버 | 공식 TypeScript MCP SDK, 같은 레포에서 HTTP 트랜스포트로 서빙 | Agent 레이어 요구 충족, 별도 배포 불요 |
| 스타일 | Tailwind CSS + shadcn/ui | 상황실 대시보드를 빠르게 높은 완성도로 |

## 알려진 리스크와 대응

- **Vercel 함수 실행 시간 제한** vs 긴 에이전트 체인 → 단계별 분할 실행 + SSE 스트리밍으로
  각 단계를 짧게 유지. 체인이 제한을 넘으면 백엔드만 Fly.io 상시 프로세스로 분리 (플랜 B)
- **API 키 비용·유출**: 서버 측 호출만, 레이트 리밋 + 데모 토큰. 심사 기간 사용량 알림 설정
- **심사 기간 장애 대비**: 외부 업타임 모니터링(UptimeRobot 등) + LLM 장애 시 캐시된 데모
  시나리오로 폴백 (판정 불가 시에도 페이지는 동작)

## 기각한 대안

- **Python FastAPI + LangGraph** (Fly.io): 오케스트레이션 표현력은 높으나 프론트와 스택이
  갈라져 1인 유지보수·Codex 위임 비용 증가. 6-에이전트 파이프라인 수준에선 과투자
- **Supabase 올인원**: Realtime은 매력적이나 Auth·Storage 등 안 쓰는 표면적이 큼. SSE로 충분
